# 目标角度与控制链路对比

当前版本 `angle-test-v19`，2026-11-05 已通过 MaixVision 启动，网页 `http://192.168.100.210:8080`。

1. 网页点“连接控制”，向下找到“目标角度测试”。
2. 填 YAW、PITCH 和速度上限（默认 30°/s）；“填入当前角度”只填表，不驱动。
3. 点“开始运动”。目标为相对驱动已保存零点的绝对机械角度，与页面角度读数同号，不使用摇杆反向映射。
4. 观察起步、匀速与到位时的抖动。到位后保持使能，可再填下一组角度。
5. “停止并保持”、非零摇杆、C 或 HOME 可中断；DISARM 仍明确失能。

YAW 限位 −150°～150°，PITCH −100°～30°。越界值在网页和板端均拒绝；不截断成另一个角度。启动需要已使能、无故障、正常限位内、新鲜机械反馈，且当前运动已停止。不修改 PI、机械零点或 Flash。

目标与开始指令只提交一次。后续使用 UART worker 的五次多项式位置轨迹，起止规划速度和加速度为零，依据速度、加速度和 jerk 上限选择时长；每个位置帧仍经过机械反馈、前置距离和限位检查。反馈追不上时暂停轨迹时间。网页空闲心跳不决定轨迹，网页失焦或断开后相机继续执行已接受的测试。相机主程序的心跳与反馈故障保护仍有效。

网页显示：

- 网页排队：点开始到发出请求的时间。
- 请求往返：HTTP 请求发出至响应收到，包含网络和服务处理，不是一程延迟。
- 板端开始：请求接受至 UART worker 开始规划。
- 首次下发：请求接受至首次有变化的位置帧发送。
- 反馈位移 ≥0.3°：请求接受至新鲜编码器反馈相对起点移动至少 0.3°；包含软起步、编码器采样和调度，不能单独当成通信延迟。

板端指标均用同一单调时钟。网页与板端不做时钟对齐，不拼接虚假的精确一程延迟。`/api/state` 的 `angle_move` 与 `/api/telemetry` 也包含目标、进度和时间记录。报告以 `PENDING / MOVING / SETTLING / COMPLETE / CANCELLED` 表示状态。

本功能排除持续网页摇杆数据到达节奏的影响，仍包含相机调度、UART 发送、电机闭环和机械结构。角度运动还使用不同于摇杆的完整到位轨迹，因此平滑程度改善不能独自证明网络是唯一原因。若本地角度运动仍抖动，可继续检查板端位置帧节奏、驱动环与机械共振；不能直接认定都是惯性。

## 当前验证

- 203 项本机 Python 测试通过：包含单次提交后网页交回控制仍完成、限位/非数字/重复请求拒绝且保留使能、HOME/取消/失能中断、跨零大位移分小步保持正确方向、轨迹速度/加速度/jerk 上限。
- 网页事件测试通过：填表和填入当前角度不启动，开始只提交一次，空值/越界不发送，停止动作独立。
- 实机只确认新版运行和自动回零保持：YAW −0.1°、PITCH 0.0°，`HOME_HOLD`、使能、无故障，角度测试状态 `IDLE`。记录：`../../research/motion_jitter_20261105/v19_startup.json`。
- 浏览器实际展示 `angle-test-v19` 与目标角度控件；没有点击“开始运动”。新增轨迹的实机抖动效果尚未验证。

v19 同时带有此前 v18 的起步/松手连续制动实现。v17 已取消手动和 TRACK 的响应倍率/误差速度补偿叠加，并避免前置距离饱和时反复清零规划速度；v18 的新增减抖效果尚无实机对比结论。
