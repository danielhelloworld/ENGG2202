# 检测阈值与阵列灯配置

本次只提供两个配置项。**已实现相机文件持久化及向 MA-USB8 请求应用；没有实现或声称驱动板 Flash 掉电保存。**官方完整命令表只公开 `t/T` 阈值增减、`e/E` 灯光开关等，没有公开 Flash 保存或这两个参数的回读/ACK。单独给驱动板断电后，需重新运行相机 demo 应用配置；不要把文件保存或串口写成功当作驱动板保存成功。

## 接线

| 驱动板 | 相机 |
| --- | --- |
| TX0 | A31 / UART1_RX |
| RX0 | A30 / UART1_TX |
| GND | GND |

新增 **A30 → RX0** 用于相机向驱动板发命令，只有之前的 TX0→A31 接线不能控制阈值和灯光。两块板分别供电，电源正极不互连，信号使用 3.3 V TTL。本次只测试麦克风，不接电机；若仍用四芯滑环，需为 RX0 增加一个通道，不能和电机收发线直接合并。

## 修改哪个文件

在 MaixVision 运行 `micarray_direction.py` 后，程序自动在**相机文件系统**创建：

```text
/root/micarray_direction/config.json
```

配置内容只有：

```json
{
  "detection_threshold": 650,
  "led_enabled": true
}
```

- `detection_threshold`：0～2000 的整数，必须是 50 的倍数。默认 650。越低越容易触发，也可能把噪声当声源。这是驱动板定位激活阈值，不是音频增益或相机算法内部的图像对比度阈值。
- `led_enabled`：`true` 开、`false` 关。只控制阵列灯，不保证驱动板电源指示灯也关闭。

通过 MaixVision 的设备文件管理或 SFTP 修改/覆盖上述**相机上的文件**并保存，程序每秒检查一次；有效变化会自动请求应用。目录内的 `config.json` 是电脑端样例，单独改电脑文件不会自动改变相机，必须上传到上述路径。也可以在运行前修改脚本顶部 `CONFIG_PATH`，使用自选的相机绝对路径。

程序调用 `save_board_config(path, value)` 时使用临时文件、flush/fsync 和原子替换保存。文件缺失时仅启动阶段创建默认值；运行期间删除、损坏、值非法或保存失败都会打印错误，不偷偷覆盖为默认配置。修改完成并恢复合法 JSON 后重新请求应用。任意额外字段也会拒绝，避免把 `save_flash` 等未知设置当作受支持参数。

## 如何下发及判断

1. 启动或阈值变化时，当前值未知，先分时发送 40 个 `t` 请求将阈值拉到公开范围下限，再发送 `阈值/50` 个 `T`，最后发送 `e` 或 `E`。每个命令间隔至少约 30 ms，主循环期间仍读取热图。默认配置约需 1.6 秒，最大阈值约需 2.4 秒，实际可能更长。
2. 此办法依赖固件按公开范围限幅、且每个字节都收到并执行。没有回读，不能验证最终绝对阈值，丢命令可能造成偏差。它不是直接写绝对值的隐藏命令。不发送 `R`，因此不会为了设阈值顺便重置波束等其他设置。
3. 已完成请求后仅切换灯光，只发送 `e/E`；同样的配置反复读取不会重复累加阈值。下发过程中若配置又变更，会重新建立基准后请求新值。
4. 控制台 `MICARRAY_CONFIG_REQUEST` 表示排队；`MICARRAY_CONFIG_SENT_UNCONFIRMED` 表示全部字节已提交 UART，**执行和保存均未确认**。诊断中的 `board_control.requested`、屏幕 `THR/LED` 都是请求值，不是驱动板回读值。
5. `MICARRAY_CONFIG_FILE_ERROR` 表示文件或格式问题，停止待发指令；修复文件即可重新排队。`MICARRAY_CONFIG_WRITE_FAILED` 表示 UART 写入失败，停止本次下发，不无限重试；修复接线/串口后重启 demo，或改变有效配置重新请求。
6. 驱动板独立重启后，相机不能从公开协议可靠识别其设置是否恢复默认，须重启 demo 重新下发。不要由 `DIRECTION_OK` 推断配置成功。

若只要此前的两线只读功能，设 `CONFIG_ENABLED=False`：程序不读写配置、不发板控命令，此时 RX0 可不接。

## 当前验证

19 项电脑端测试通过，包括合法性检查、原子保存失败不损坏旧配置、热更新、损坏恢复、重复加载不重复发、灯光单独请求、串口短写、只读/控制两种主入口，以及有界阈值固件模型。没有实板参数回读、灯光效果、阈值生效或掉电保存证据。
